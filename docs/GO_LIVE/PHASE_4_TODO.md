## Completed this session

DEV-owned data-subject-rights endpoints (§4.2), built on the Phase 2 auth now on `dev`:

- **Self-service DSAR export (JSON + PDF).** `GET /v1/privacy/export` (JSON) and `GET /v1/privacy/export/pdf`
  (pdfkit). Aggregates the caller's profile + each child's growth/milestones/vaccinations/allergies/
  conditions + appointments + reports. `passwordHash` is `select:false` and never included.
- **Data portability.** The JSON export is the machine-readable copy.
- **Right to erasure (soft-delete + 30-day grace).** `POST /v1/privacy/erasure` sets
  `User.deletionRequestedAt`, archives the subject's children (`ResourceStatus.ARCHIVED`), audits
  `ERASURE_REQUESTED` to `SystemLog` (no PII), ends the session (clears the cookie), and returns the
  scheduled hard-delete date (+30d).
- **Security.** All `/v1/privacy/*` routes use the strict `JwtVerifiedGuard`; the data subject is always
  the token's `sub` — never a URL param — so a user can only export/erase their **own** data. This
  hardens the pre-existing stale-branch export which took `userId` from the URL under a placeholder guard.
- **User migration** `AddUserDeletionRequestedAt` (nullable timestamp).
- **Web self-service.** `/dashboard/account/privacy` page — Download JSON / Download PDF / Delete account
  (confirm dialog → soft-delete → logout). The old `/dashboard/account/settings` hard-delete
  (`DELETE /users/:id`) was rerouted through the same soft-delete erasure flow (POPIA fix).
- **Tests.** `privacy.service.spec.ts` integration suite passes on real Postgres (export shape + scoping,
  passwordHash omitted, PDF `%PDF` bytes, erasure sets `deletionRequestedAt` + archives children).
