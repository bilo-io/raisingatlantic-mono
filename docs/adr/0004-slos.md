# ADR 0004 — Service Level Objectives (DRAFT)

**Status:** DRAFT — pending `PRODUCT` sign-off
**Date:** 2026-06-03
**Phase:** [Go-Live Phase 7 — Observability & Monitoring](../GO_LIVE/DEV.md#phase-7-observability--monitoring)

## Context

We are launching a regulated healthtech product on Cloud Run + Cloud SQL in
`africa-south1`. Once real users are in, we need an explicit, measurable
contract about how reliable the system has to be, so we can:

1. Tell users (and the Information Regulator) what to expect.
2. Decide objectively when to slow feature work in favour of reliability work.
3. Wire alert policies that fire when we are at risk of breaching the contract,
   not when the system merely deviates from a Platonic ideal.

This ADR proposes the launch-week SLO targets. The numbers below are drawn
from the DEV.md TL;DR tier 1 follow-up section and are **DRAFT** until
`PRODUCT` confirms them.

## Decision (DRAFT)

### Availability SLO

**99.5% successful HTTP responses per calendar month, measured on the API.**

- Service: `ra-api-prod` (Cloud Run).
- Metric: 1 − (5xx response count ÷ total response count) over a rolling 30
  calendar day window.
- Excludes: client-induced 4xx, planned-maintenance windows announced at least
  24 hours in advance on the status page.
- Error budget: 0.5% of total requests in the window. At 50% budget burn we
  raise an internal warning; at 100% we freeze non-critical deploys until the
  next budget window opens.

### Latency SLO

**95% of HTTP requests served in under 500 ms at the API edge.**

- Service: `ra-api-prod`.
- Metric: p95 of `http.server.duration` (OpenTelemetry histogram), measured
  in 5-minute buckets, aggregated to a 30-day rolling window.
- Excludes: file-upload endpoints, AI-summary endpoints (separate SLO TBD).

### Web availability

**Tracked as a derived signal**, not a separate SLO at launch. The Cloud
Monitoring + BetterStack uptime check against `https://raisingatlantic.com/`
must show 99% over 30 days. If this regresses, treat it as a P1.

## Error budget policy

| Budget remaining | Posture |
|---|---|
| ≥ 50% | Normal: feature work proceeds, deploys land on `dev` → `test` → `main` as usual. |
| 50 – 25% | Caution: prioritise reliability fixes over new features in the next sprint. |
| < 25% | Lockdown: only critical bug fixes and reliability work land on `main`. Deploys require an explicit override note in the PR description. |
| 0% | Freeze: no non-critical merges to `main` until the rolling window restores budget. |

## Alerting

These SLOs are operationalised in Terraform under `infra/envs/prod/monitoring.tf`:

- `alert_error_rate` — burns the availability budget faster than monthly.
- `alert_p95_latency` — p95 > 500 ms over 10 minutes.
- `alert_uptime_api` — uptime probe failure.

All three route to `#alerts-prod` (Slack) via `google_monitoring_notification_channel.slack_alerts_prod`. Low-severity signals route to the email digest.

## Out of scope (not yet decided)

- Mobile-app crash-free session rate target.
- AI-summary endpoint latency target.
- Per-tenant SLOs for B2B practices on enterprise tiers.
- Multi-region failover RTO/RPO numbers (see [Phase 1.5 §1.5](../GO_LIVE/DEV.md#15-database-neon-vs-cloud-sql) for current baseline).
